# 什么是RAG?

**RAG:Retrieval-augmented Generation** 即**检索增强生成** 

## RAG 出现的原因

1. 知识有截止日期：大模型的知识来自于训练数据，而训练数据有时间窗口
2. 大模型不知道私有数据
3. 大模型会有幻觉（幻觉：装模像样地说出一句胡编乱造的东西）

## 所以RAG做了什么

Retrieval-augmented Generation：从外部检索相关资料、检索到的资料用于增强上下文、然后生成回答

RAG不是万能的，它是一种让大模型基于真实、可更新的知识来回答问题的技术方案。它和微调、Prompt Engineering等技术是互补的

# RAG工作流程

一个完整的 RAG 系统其实分为两个大阶段：索引阶段（离线） 和 查询阶段（在线）

## 索引阶段

1. 文档加载：各种格式转为纯文本
2. 文档切割：长文档 → 文本块（Chunk） *这里涉及到了文档切割策略
3. 向量化：每个文本块转换成一个数学向量（Embedding）
4. 存入向量数据库：高效的进行相似度搜索

## 查询阶段

1. 用户提问向量化
2. 相似度搜索
3. 构造增强Prompt
4. 大模型生成回答

索引阶段（离线）：文档加载 → 文档切割 → 文本向量化 → 存入向量数据库
查询阶段（在线）：用户提问 → 问题向量化 → 向量检索 → 构造增强Prompt → 大模型生成回答
以上是最朴素的RAG工作流程，也称为Naive RAG
实际生产中，还会加入查询改写、多路召回、重排序（Re-rank）等高级技术

# 微调和RAG的区别

## 微调
Fine-tuning,拿一个已经训练好的大模型，用自己的数据对他进行进一步的训练，包括：

1. 全量微调：更新模型的所有参数，需要大量GPU资源
2. 参数高效微调：LoRA，只训练一个很小的“低秩适配器”
3. 指令微调：“指令-回答”格式的数据进行微调，目的是让模型听懂指令

所以：微调是上课以后进行闭卷考试，RAG是开卷考试

## 区别

1. 知识更新方式:微调要更新知识，要重新训练模型；RAG只需要把新的产品手册替换掉知识库里的旧文档，并更新索引
2. 准确性：RAG可追溯、可验证，准确性更高
3. 语言风格控制：微调更擅长控制模型用什么风格回答问题
4. 成本：微调的初始成本高（大量高质量训练数据、GPU资源）但推理阶段的成本较低；RAG初始成本较低，但每次检索都消耗token

## 如何选用？

* 微调场景：一、输出特定风格或格式；二、学会某种能力而非知识；三、数据量不大且不经常更新
* RAG场景：一、严格基于特定文档；二、知识更新频繁；三、涉及大量私有数据；四、回答需要可追溯、有出处

实际更多的是RAG + 微调

# 文档切割
原因：大模型的上下文窗口有限

## 策略

1. 固定大小切割：可能会导致语义问题 - 重叠（overlap）
2. 递归字符切割： LangChain框架中RecursiveCharacterTextSplitter的实现方式，核心思想是按照文本的自然边界来切，而不是固定字符数量切割
3. 基于文档结构切割：只适用于格式规范的文档
4. 语义切割：
先把文档按句子切分，然后计算语义相似度（Embedding模型把句子转成向量，然后计算余弦相似度），相似度突然下降的地方就是切割点
切割质量最高，但成本最大
5. Agent驱动的智能切割：理论上效果最好，但成本也是最高的

## 实际应用
起步阶段：递归字符切割
优化阶段：基于文案结构切割
进阶阶段：语义切割或“父子块策略”（存储小块用于精准检索，给大模型包含上下文的父块）

# Re-rank 重排序

出现原因：RAG检索阶段用的是Bi-Encoder(双编码器)，也就是Embedding模型，它的工作方式是把查询和文档分别编码成向量，然后计算余弦相关度来判断相关性，它对查询和文档是分别处理的，只能生成一个“泛平均化的”的语义向量，无法针对具体的查询做优化

具体来讲：一、信息压缩损失；二、缺乏查询意图感知

## Cross-Encoder(交叉编码器)
Re-rank用的是Cross-Encoder，把查询和文档拼在一起
```agsl
[CLS] 用户的问题 [SEP] 检索到的文档内容 [SEP]
```
然后把整个输入放进Transformer模型，通过自注意力机制（Self-attention），让查询中的每个词都能与文档中的每个词进行交互

缺点是太慢了

## 两阶段检索
第一阶段用粗排，Bi-Encoder;第二阶段用精细化重排序，Cross-Encoder

## 主流的Re-rank模型

Cohere Rerank:SaaS API服务，目前用的最多，省心，适合预算充足的情况
BGE-Reranker：很多国内企业的选择，开源
ms-marco-MiniLM：轻量，体积小速度快，适合GPU不多或对延迟要求很高的场景
Jina Reranker：支持多语言

## 效果
提高准确率，降低幻觉

## 实战中的使用
首先，候选数量设置为50到100个，再重排到Top-5或Top-10；其次，设置重排序条件触发机制，比如只在初排Top-1的分数低于某个值的时候才启动重排序

但对于复杂查询，重排序收益很高，建议始终开启

# Embedding

## Embedding的发展迭代

1. 静态词向量时代（2013）:
    * Word2Vec：国王 - 男人 + 女人 = 女王
    * 两种训练方式：CBOW(连续词袋模型，用上下文来预测中间的词)/Skip-Gram（跳字模型，用一个词来预测上下文）
    * 缺陷：每个词生成一个固定的向量
2. 上下文嵌入时代（2018）：
    * BERT:用Transformer的自注意力机制代替传统的循环神经网络，实现了真正的上下文理解
    * 两种训练方式：MLM(遮盖语言模型：随机遮盖15%的词，训练模型通过上下文预测被遮盖的词)/NSP(给模型两句话，让他判断a是否为b的下一句)
    * 缺陷：上下文窗口小
3. 融合与优化时代（2023至今）：
    * BGE-M3:
      * 多粒度：Multi-Granularity，能处理句子、段落、篇章、文档等不同粒度的输入，最大支持 8192 tokens。
      * 多功能：Multi-Functionality，一站式集成稠密检索（稠密向量→语义检索）、稀疏检索（稀疏向量→关键词匹配）和多向量检索（更精细的匹配）三种功能
      * 多语言：Multi-Language，支持一百多种语言
    * text-embedding系列：简单好用
4. 基于大模型的Embedding（2025年）
直接用大模型来做Embedding
2025 年字节跳动发布的 Seed1.5-Embedding 在 MTEB 榜单上达到了中英文 SOTA 水平，证明了 LLM-based Embedding 的巨大潜力。

## 怎么选择Embedding模型
1. MTEB排行榜
2. 中文场景优先国产模型：BGE、M3E、ACGE
3. 如果文档很长，选用支持长上下文的模型
4. 简单省事 → API服务；私有化部署 → 开源模型

# 向量数据库

它使用特殊的索引结构（如HNSW、IVF、PQ等等），能够在海量向量中实现毫秒级的近似最近邻搜索（ANN）

## 核心原理：用空间换时间

### 目前主流的索引思路：
1. HNSW:顶层到底层逐层查找，查询速度快，召回率高，是目前大多数向量数据库的默认选择
2. IVF：先分区再搜索，内存效率高，适合超大规模数据，但因为只搜索部分桶，会损失一点召回率
3. PQ：压缩存储，在内存有限的场景下很有用，通常PQ会和IVF结合使用

### 目前主流的向量数据库

1. Milvus:最好用，但部署和维护有点门槛，通常需要kubernetes来编排，需要DevOps经验
2. Pinecore：全托管的SaaS服务。省心省事，但付费且数据存在第三方平台上
3. Weaviate：支持混合检索（向量检索 + BM25）,还内置了多种Embedding模型的集成，可以直接在Weaviate内部完成文本到向量的转换。适合中小规模的应用
4. Chroma：轻量、简单，但不支持分布式，也没有安全机制，所以不太适合生产环境
5. Qdrant：用 Rust 语言写的，所以单机性能非常强，也支持丰富的过滤条件和混合检索不过它的分布式方案相对来说还比较新，如果你需要多节点的集群部署，可能需要多测试一下稳定性。

* 传统数据库的向量拓展：PostgreSQL 的 pgvector 插件、Elasticsearch 的向量搜索功能。如果你的项目已经在用 PostgreSQL 或 ES，不想为了 RAG 再引入一套新的数据库组件，用它们的向量扩展也是一个很务实的选择。
